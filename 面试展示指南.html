3 分钟标准版
3分钟版

背景：在运维场景中，告警发生后信息分散在日志、监控、数据库等多个系统中，排查路径依赖个人经验，效率低且不可复现。

架构设计：我把系统拆成两层——API 层用 FastAPI 提供 RESTful 接口和 SSE 流式输出；Agent 层设计了双工作流。简单知识问答走 ReAct 模式，边思考边调用工具，响应路径短；复杂告警诊断走 LangGraph 的 Plan-Execute-Replan 状态图，先生成计划，每执行一步把结果写回状态，再决定继续、重规划还是结束。两种工作流共享统一的工具层。

工具层解耦：通过 MCP 协议统一接入了 13 个工具，分布在 3 个独立的 MCP Server 中——日志服务、监控服务、Ops 服务（只读 MySQL + 联网检索）。客户端实现了指数退避重试拦截器，最多 3 次，失败后返回错误结果而非抛异常，让 Agent 可以优雅处理工具失败。

可靠性设计：系统有四层降级防线——Planner 结构化输出失败会降级为纯文本解析，再失败返回默认计划并标记 degraded；Executor 单步失败会记录原因继续执行；Replanner 有三层收敛机制防止无限循环；整体有总时间预算超时控制。MySQL 工具实现了只读安全边界，四重校验：前缀白名单、关键字黑名单、多语句检测、schema 白名单。

评测体系：构建了 600 条可复现 RAG 查询，按模板隔离防止数据泄漏，在 dev 上做了 54 组参数对照实验，锁定配置后在 held-out test 上 Hit@5 从 95.83% 提升到 98.33%。Agent 评测 30 条任务 3 轮重复，任务成功率 80%，工具调用成功率 100%。

4.1 系统架构设计 对应：架构设计和开发

双 Agent 工作流：按场景分离

设计了两套独立的工作流，按查询复杂度路由：

维度ReAct 对话 AgentPlan-Execute-Replan 诊断 Agent
适用场景知识问答、简单查询多步故障诊断、证据链排查
核心机制LangChain create_agent + 工具绑定LangGraph StateGraph 三节点状态图
状态管理MemorySaver + trim_messages 中间件TypedDict + operator.add reducer
LLM 调用单轮或少轮多轮（plan → execute × N → replan）
收敛控制消息修剪（保留首条 System + 最近 6 条）三层收敛：MAX_STEPS=8 + replan 截断 + 二次检查

Plan-Execute-Replan 的"宏观规划 + 微观自治"

这是最值得讲的架构创新点——不是 Plan-Execute-Replan 和 ReAct 二选一，而是嵌套式融合：

Planner（规划做什么） → Executor（ReAct 自主选工具） → Replanner（是否调整计划）
  • Planner 负责任务分解，避免纯 ReAct 在中途迷失方向
  • Executor 内部是 ReAct 循环，LLM 自主编排"先查 topic_id 再查日志"这类链式依赖
  • Replanner 根据中间结果决定 continue/replan/respond，实现动态调整

状态管理：operator.add reducer

class PlanExecuteState(TypedDict):
    input: str
    plan: list[str]
    past_steps: Annotated[list[tuple], operator.add]  # 增量追加
    degraded: bool
    response: str

每个节点返回的 past_steps 会被追加到状态中而非覆盖，Executor 每次只返回单元素列表，状态自动累积所有历史步骤。同时，每次诊断生成全新 uuid4 thread_id，避免跨请求 checkpoint 状态污染。

4.2 高可用与容错设计 对应：高并发、稳定性

四层降级防线

层级触发条件降级策略代码位置
第 1 层Planner 结构化输出失败降级为纯文本解析（正则匹配多种格式）planner.py
第 2 层纯文本解析也失败返回默认计划 + degraded=True 标记planner.py
第 3 层Executor 单步执行失败记录失败原因到 past_steps，继续执行下一步executor.py
第 4 层Replanner 决策异常捕获异常，默认继续执行原计划replanner.py

Replanner 三层收敛机制（防止 Agent 无限循环）

  • 硬性上限：MAX_STEPS=8，超过强制生成响应
  • Replan 收敛：新步骤数 ≤ 当前剩余步骤数，否则截断（防止计划膨胀）
  • 二次检查：已执行 ≥ 5 步时，即使 LLM 说 replan 也强制 respond
  • Prompt 级口诀："优先结束 > 保持不变 > 调整计划"

总时间预算超时控制

deadline = loop.time() + total_timeout  # 默认 1800s
while True:
    remaining = deadline - loop.time()
    if remaining <= 0:
        raise TimeoutError
    event = await asyncio.wait_for(
        stream.__anext__(), timeout=remaining
    )
    yield event

不是对单个节点设超时，而是对整个诊断流程设总时间预算。超时后发出 stage="timeout" SSE 事件并 aclose() 终止图执行。

MCP 工具指数退避重试

  • 最多 3 次重试，退避 1s → 2s（指数退避）
  • 异常和 isError=true 统一处理（不会因 MCP 返回错误而崩溃）
  • 失败后返回 CallToolResult 而非抛异常，Agent 可继续运行
  • 最终只记录一次逻辑调用结果（避免指标重复计数）

4.4 数据安全与隔离 对应：数据隔离

thread_id 跨请求隔离

每次诊断生成全新 uuid4 thread_id，不复用调用方 session_id。因为 past_steps 使用 operator.add reducer，相同 thread_id 会把历史增量 merge 进来，导致跨请求状态污染。这是非常 subtle 的 bug 防御。

MySQL 只读安全边界（四重防护）

_READ_ONLY_PREFIXES = ("select", "show", "describe", "desc", "explain")
_FORBIDDEN_SQL = re.compile(
    r"\b(insert|update|delete|replace|merge|alter|drop|truncate|"
    r"create|rename|grant|revoke|call|execute|prepare|handler|"
    r"load|outfile|dumpfile|lock|unlock|set|use)\b", re.IGNORECASE,
)
防护层检查内容
1. 前缀白名单只接受 SELECT / SHOW / DESCRIBE / EXPLAIN
2. 关键字黑名单14 个写入/管理关键字（insert/update/delete/drop...）
3. 多语句/注释检测拒绝 ; -- /* #
4. schema 白名单 + 行数限制只允许配置的 schema，自动注入 LIMIT 200
面试时主动强调

应用层校验是第二道防线，不能替代数据库只读账号。生产环境必须同时使用数据库侧权限控制。9 个参数化测试覆盖了 DELETE、SQL 注入、INTO OUTFILE 等攻击向量。

五、面试官高频问题与参考回答
以下问题按类别分组，每个回答都基于项目实际代码和评测数据，可直接引用。
系统设计类
为什么设计双 Agent 工作流？不能只用一种吗？

两种工作流适合不同场景。ReAct 适合短链路、边思考边调用工具的开放问答，响应路径短，延迟低；Plan-Execute-Replan 适合多证据排障，先生成计划，每执行一步把结果写回状态，再决定继续、重规划或结束。代价是后者 LLM 调用次数更多，所以设置了最大步骤数和强制收敛条件。

如果只用 ReAct，在复杂诊断场景下容易在中途迷失方向——比如查了 CPU 但忘了查日志，或者查了日志但不知道下一步该做什么。如果只用 Plan-Execute-Replan，简单知识问答也要走完整的规划-执行-重规划流程，延迟会从秒级变成几十秒。

Plan-Execute-Replan 和纯 ReAct 有什么本质区别？

核心区别是是否有全局计划。纯 ReAct 是"走一步看一步"，LLM 每轮根据当前观察决定下一步；Plan-Execute-Replan 是"先规划再执行"，Planner 一次性生成完整计划，Executor 按计划执行，Replanner 根据结果动态调整。

我的设计中，两者不是二选一，而是嵌套融合：外层是 Plan-Execute-Replan 做宏观调度，每个 Execute 步骤内部是 ReAct 循环做微观工具编排。比如 Planner 生成"查询 CPU → 查询日志 → 分析根因"，Executor 执行"查询日志"这一步时，ReAct 循环会先调 search_topic_by_service_name 拿到 topic_id，再调 search_log 查日志——这个链式依赖不需要 Planner 预知，Executor 自主完成。

如果让你设计一个支持百万并发的 Agent 系统，你会怎么做？

当前项目是单机服务，如果要支持百万并发，我会从以下几个方向改造：

  • 无状态化：当前诊断 Agent 每次生成新 thread_id 已经是无状态的，但 MemorySaver 是内存级 checkpoint，需要替换为 Redis 或外部存储
  • 异步队列：Agent 诊断是长耗时任务（P50=9.36s），不适合同步等待。用消息队列（如 Kafka）解耦请求和执行，前端通过 SSE 或 WebSocket 订阅结果
  • LLM 调用限流：LLM API 是瓶颈，需要实现令牌桶限流 + 请求队列 + 超时降级
  • 工具层熔断：当前重试拦截器可以扩展为熔断器，连续失败达到阈值后快速失败，避免雪崩
  • MCP 连接池：当前是单例客户端，高并发下需要连接池或按请求隔离
  • 水平扩展：FastAPI 无状态可水平扩展，Milvus 本身支持分布式部署
MCP 协议的价值是什么？为什么不直接写工具函数？

MCP 把工具发现、参数 schema 和调用协议统一起来，Agent 不需要为日志、监控、数据库分别维护私有适配代码。项目使用 3 个独立 MCP Server 隔离不同能力，并在客户端拦截器里统一处理指数退避和指标采集。

如果直接写工具函数，每个工具的异常处理、重试逻辑、指标采集都要重复实现，而且工具变更需要重新部署 Agent 服务。用 MCP 后，日志服务升级不需要动 Agent 代码，只要 MCP 接口不变。这和微服务架构的思路一致——通过协议解耦，独立部署和扩展。

技术深度类
LangGraph 的 StateGraph 是怎么工作的？

StateGraph 是 LangGraph 的核心，基于状态机实现。定义一个 TypedDict 作为状态，添加节点（每个节点是一个函数，接收状态返回状态更新），添加边（包括条件边）。编译后得到一个可执行的图，支持流式执行、checkpoint 持久化和中断恢复。

我的项目中，状态是 PlanExecuteState，三个节点是 planner、executor、replanner。planner → executor 是固定边，executor → replanner 是固定边，replanner 出去是条件边——根据 should_continue 函数判断走回 executor 还是到 END。编译时传入 MemorySaver 作为 checkpointer，支持中断恢复。

operator.add reducer 是什么？为什么要用它？

LangGraph 的状态更新默认是覆盖语义，但有些字段需要追加。Annotated[list[tuple], operator.add] 告诉 LangGraph 这个字段用 operator.add（即 list.__iadd__）作为 reducer——每次节点返回的值会被追加到状态中，而非覆盖。

我的 past_steps 用它是因为 Executor 每次只执行一个步骤，返回 {"past_steps": [(task, result)]}（单元素列表），但状态中需要累积所有历史步骤。如果用默认覆盖语义，每轮都会丢失之前的执行记录。

这个设计也带来一个 subtle 的 bug：如果复用相同的 thread_id，checkpoint 会把上一次诊断的历史增量 merge 进来，导致跨请求状态污染。所以每次诊断必须生成全新的 uuid4 thread_id。

SSE 流式输出是怎么实现的？

用 sse_starlette 的 EventSourceResponse 实现。FastAPI 路由函数返回一个 async generator，每个 yield 对应一个 SSE 事件。LangGraph 的 astream(stream_mode="updates") 会推送状态增量，我把这些增量格式化为 6 种事件类型（status/plan/step_complete/report/complete/error）。

关键设计是总时间预算超时：不是对单个节点设超时，而是对整个诊断流程设总预算（默认 1800s）。每次取事件都按剩余预算等待，超时后发出 timeout 事件并在 finally 中 aclose() 终止图执行。

RAG 评测的防泄漏切分是什么？为什么需要？

如果同一个问题模板的不同改写分别出现在 train 和 test 中，模型在 train 上调参时已经"见过"类似问题，test 上的指标会虚高。我的做法是按问题模板分组：20 个模板中，0-11 号→train（360 条），12-15 号→dev（120 条），16-19 号→test（120 条）。同一模板的 6 种风格改写只会在一个集合中。

调参只在 dev 上做（54 组对照实验），锁定配置后只在 test 上跑一次汇报最终结果。这样 test 指标反映的是真正的泛化能力。风格改写包括正式/口语/简洁/约束/场景/复盘，别名轮转（如"CPU 飙高"/"处理器负载过高"/"HighCPUUsage"），增强泛化性评测。

Milvus 的索引你选了什么？为什么？

选了 IVF_FLAT 索引，度量方式用 L2（欧氏距离），nlist=128（聚类中心数），检索时 nprobe=10（探测的聚类数）。Collection schema 包含 id、vector（512 维 BGE-small-zh）、content（8000 字符）、metadata（JSON 存来源/文件名/标题）。

IVF_FLAT 先聚类再在簇内精确搜索，相比 FLAT 全量搜索大幅降低延迟，相比 IVF_PQ 不做乘积量化压缩，精度更高。在 5 份运维文档的数据规模下，P95 检索延迟 0.74ms，精度和速度都够用。如果数据量到百万级，可以考虑切换 HNSW 或 IVF_PQ。

高并发与稳定性类
如果工具调用超时了怎么办？

三层防护：第一层，MCP 客户端的 retry_interceptor 会自动重试，最多 3 次，指数退避 1s → 2s。第二层，重试全部失败后返回 isError=True 的 CallToolResult 而非抛异常，Executor 把错误信息作为 ToolMessage 回灌给 LLM，LLM 知道工具失败了可以换一个工具或基于已有信息继续。第三层，整个诊断流程有总时间预算超时（默认 1800s），超时后发出 timeout 事件并终止。

当前可以继续改进的点：按错误码区分可重试和不可重试错误（如 4xx 不重试、5xx 重试），加入 jitter 避免重试风暴，加入熔断器在连续失败时快速失败。

如何防止 Agent 无限循环？

三层收敛机制：第一层，硬性上限 MAX_STEPS=8，已执行步骤超过 8 直接强制生成响应。第二层，replan 收敛约束，新步骤数必须 ≤ 当前剩余步骤数，否则截断，防止 replan 导致计划膨胀。第三层，二次检查，已执行 ≥ 5 步时即使 LLM 说 replan 也强制 respond。

此外，Executor 内部的 ReAct 循环也有 max_iterations=5 上限，达到后解绑工具强制 LLM 收尾。LangGraph 编译时还设了 recursion_limit=50 防止图节点间无限跳转。Prompt 层面也写了决策优先级口诀："优先结束 > 保持不变 > 调整计划"。

如果 LLM 返回的结构化输出解析失败怎么办？

双轨制设计：首选 llm.with_structured_output(Plan) 走 Function Calling；失败后调用 _plan_with_plain_text() 走纯文本兜底，再用正则 _parse_plan_steps() 解析"步骤1:"、"1."、"-"等多种格式。这保证了对不支持 Function Calling 的本地小模型（如 Ollama qwen3:8b）的兼容。

如果纯文本解析也失败，返回默认计划 ["收集相关信息", "分析数据", "生成报告"] 并通过 degraded: True 显式标记，前端可据此提示用户。Replanner 决策也是同样的双轨制——structured output 失败后降级为纯文本解析。

你的系统当前有什么瓶颈？如果要上生产还需要做什么？

当前主要瓶颈和待改进项：

  • LLM 调用是串行瓶颈：Plan-Execute-Replan 每步都调 LLM，P50=9.36s。生产场景需要考虑流式输出 + 异步队列
  • MemorySaver 是内存级：服务重启丢失状态，需替换为 Redis 或数据库持久化
  • 缺少鉴权和限流：当前是实习作品，没有身份认证、API 限流、审计日志
  • CLS/Monitor 是演示数据：需要替换为真实云日志和监控 API
  • 缺少熔断和并发限流：当前重试拦截器可扩展为熔断器
  • 测试覆盖不足：42.67% 语句覆盖率，Replanner 和 API 集成测试待补齐
  • 缺少提示注入防护：Agent 接收用户输入直接进 Prompt，生产环境需要输入消毒

这些边界我主动说明，反而比把 Demo 包装成生产系统更可信。

评测与数据类
Hit@5 是什么？为什么不直接用准确率？

每条查询预先标记期望来源文档，如果该文档出现在前 5 个检索结果中，这条查询记为命中。Hit@5 衡量"相关证据是否被召回"，不等于最终答案正确率。因为即使检索到了正确文档，LLM 也可能生成错误答案；反之检索没命中，LLM 也可能靠自身知识回答正确。

所以项目同时记录多个指标：Hit@5（召回率）、MRR@5（排序质量）、失败归因（ranking_error vs semantic_miss）、Agent 任务成功率（端到端正确率）、工具调用成功率。多维度指标才能全面评估系统效果。

这次 RAG 优化具体做了什么？Hit@5 怎么提升的？

在 dev 集上做了 54 组对照实验，覆盖 4 个维度：切分策略（markdown-header / plain）、Chunk Size（400 / 800 / 1200）、Overlap（0 / 50 / 100）、Top-K（1 / 3 / 5）。

关键发现：在短 Markdown 运维 SOP 语料上，plain（纯递归字符切分）反而优于 markdown-header。因为按 h1/h2 切会破坏 SOP 的"检查步骤"段落完整性，而 plain 1200 字大分片能保留完整排查流程。Overlap 在短文档场景下反而有害——产生重复分片干扰排序。

锁定 plain / 1200 / 0 / Top-5 后，在 held-out test 上 BGE Hit@5 从 95.83% → 98.33%，MRR@5 从 68.79% → 76.06%。BM25 baseline 只有 89.17%，说明语义检索在运维场景下明显优于字面匹配。

600 条评测数据是怎么生成的？会不会有偏差？

5 个种子文档 × 20 个问题模板 × 6 种风格改写 = 600 条。风格包括正式/口语/简洁/约束/场景/复盘，别名轮转（如"CPU 飙高"/"处理器负载过高"/"HighCPUUsage"），增强泛化性。

偏差肯定存在：数据是规则构造的，不是真实用户查询；600 条标签 review_status=pending，尚未人工复核；30 条 Agent 任务的期望工具都是 retrieve_knowledge，不能证明所有 13 个工具都完成了端到端评测。所以我表述为"可复现离线查询集"而非"人工标注评测集"。下一步是人工复核标签，并补充 10-20 条脱敏真实告警。

AI 与后端结合类
你怎么看待 AI Agent 在后端系统中的应用？

Agent 不是替代传统后端，而是在规则引擎和纯人工之间的补充。传统运维自动化依赖预写脚本和规则，灵活但无法处理未预见场景；纯人工灵活但慢且依赖个人经验。Agent 的价值是在已知工具集上自主编排——工具是确定性的（查日志、查监控、查数据库），编排是灵活的（LLM 根据告警上下文决定调用顺序）。

但 Agent 的可靠性挑战比传统后端大得多：LLM 输出不确定、可能幻觉、可能无限循环。所以我的项目花了大量精力在可靠性设计上——四层降级、三层收敛、总时间预算超时、工具重试降级。这些工程保障才是 Agent 能落地的关键，而不是 Prompt 写得多好。

你的项目和抖音的服务架构有什么关联？

抖音服务架构团队关注亿级用户的高可用、弹性、低成本架构。我的项目虽然规模不同，但工程思路是相通的：

  • 稳定性：四层降级 + 三层收敛 + 超时控制，和生产系统的容错设计思路一致
  • 系统解耦：MCP 统一工具层和微服务架构的思路一致，通过协议解耦独立部署
  • 数据隔离：thread_id 隔离和 SQL 只读边界，对应生产系统的租户隔离和权限控制
  • 可观测性：P50/P95 指标采集，和生产系统的监控告警思路一致
  • 评测驱动：54 组对照实验和 A/B 测试的思路一致，用数据驱动决策而非拍脑袋

规模上的差距我很清楚——当前是单机服务，抖音是亿级并发。但工程思维和方法论是可迁移的，这也是我投递这个岗位的原因。

你在这个项目中遇到的最大技术挑战是什么？

最大挑战是Agent 的可靠性设计。早期版本经常出现两个问题：一是 LLM 陷入无限工具调用循环，比如反复查同一个日志；二是 LLM 的"完美主义倾向"——总觉得信息不够，不断 replan 导致计划膨胀。

解决过程：第一步加了 MAX_STEPS=8 硬性上限，治住了无限循环。第二步发现 replan 后新步骤数可能比原来还多，加了"新步骤数 ≤ 剩余步骤数"的截断约束。第三步发现即使有约束，LLM 在 5 步以后还是倾向于 replan，加了"≥5 步强制 respond"的二次检查。最后在 Prompt 里写了决策优先级口诀"优先结束 > 保持不变 > 调整计划"。

这个过程让我深刻理解到：Agent 系统的核心难点不在 Prompt 工程，而在于如何对不确定性输出做工程约束。这和传统后端用类型系统、事务、锁来约束确定性逻辑是不同的挑战。

可能被追问的"弱点"及应对
你的项目数据量太小（只有 5 份文档），能说明什么？

数据量确实不大，但我的重点是评测方法论而非绝对指标。5 份文档覆盖了 5 类典型运维场景（CPU/内存/磁盘/服务不可用/慢响应），600 条查询通过模板 × 风格改写保证了多样性。防泄漏切分确保 test 指标反映泛化能力。这套方法论在数据量增大时同样适用——实际上数据量越大，防泄漏切分和参数对照实验的价值越高。

你是 AI 方向的，为什么投后端岗？

我的项目虽然是 Agent 系统，但核心工作量在后端工程——FastAPI 接口设计、SSE 流式协议、MCP 服务拆分、SQL 安全边界、重试降级、可观测性、测试和代码规范。AI 部分用的是现成模型和框架，真正花精力的是怎么让 Agent 系统可靠、可观测、可评测。这和后端工程的关注点是一致的。

而且抖音服务架构团队也有"参与机器学习与异构计算系统研发"的要求，我的 AI 背景反而是加分项——我既懂 Agent 和 RAG 的技术原理，又有后端工程实践能力。

你用的是 LangChain/LangGraph 框架，如果不用框架你能实现吗？

可以。LangGraph 的 StateGraph 本质是状态机——节点是函数，边是条件判断，checkpoint 是状态持久化。我完全可以基于 asyncio 和 dict 实现同样的状态流转。用框架的原因是：第一，框架处理了并发安全、状态序列化、中断恢复等底层细节；第二，框架的生态（如 langchain-mcp-adapters）可以直接复用；第三，框架有社区维护和版本迭代。

但我对框架的内部原理是了解的——比如我知道 operator.add reducer 会导致跨 thread_id 状态污染，所以每次生成新 uuid4；我知道 stream_mode="updates" 推送的是状态增量而非全量。这些理解让我能在框架出问题时快速定位。

这个项目是你一个人做的还是有团队？

如果是个人项目，如实说"独立开发"。项目方建议：只有确实存在团队协作且承担核心模块时，才保留"核心开发"。个人项目体现的是独立完成全栈能力——从架构设计到代码实现到测试评测，反而是加分项。
