# 消息队列积压告警处理方案

## 文档元数据

- 场景：Kafka/RabbitMQ 消费积压、消费延迟、死信增长
- 常见告警：ConsumerLagHigh、QueueDepthHigh、OldestMessageAgeHigh
- 适用对象：Kafka Consumer Group、RabbitMQ Queue
- 风险级别：P1/P2
- 变更原则：先确认生产速率、消费速率和最老消息年龄，再决定扩容或限流

## 现象与影响

队列深度或 consumer lag 增长会导致数据延迟、异步任务超时和下游状态不一致。积压量为零、队列查询失败、消费组不存在是三种不同状态，诊断报告必须分别表达。

## 核心证据

- 当前积压量及增长斜率；
- 最老消息年龄；
- 生产/消费速率；
- 活跃消费者和分区分配；
- 消费错误、重试、死信和反序列化失败；
- Broker 健康、磁盘和网络；
- 最近发布、扩缩容和流量变化。

## 排查步骤

### 步骤一：判断是否持续积压

至少观察两个采样窗口。短时峰值后快速回落通常不需要高风险操作；积压持续增长表示生产速率高于有效消费速率。

### 步骤二：检查消费者

- 实例是否存活且 Ready；
- 消费组是否频繁 rebalance；
- 单条消息处理耗时是否升高；
- 是否因毒消息反复重试；
- 分区数是否限制并行度；
- 下游数据库或 API 是否变慢。

### 步骤三：检查 Broker

关注磁盘使用率、网络、ISR、分区离线、连接数和请求延迟。Broker 正常不代表消费者正常。

### 步骤四：定位消息类型

按 topic、partition、routing key、错误码或业务类型分组。若少量毒消息阻塞分区，需要保留消息标识和失败原因，避免直接清空队列。

## 根因判定

| 证据组合 | 可能根因 |
|---|---|
| 生产速率突增、消费耗时稳定 | 容量不足 |
| 消费速率下降、下游延迟升高 | 下游依赖瓶颈 |
| 单分区积压明显 | 分区热点或毒消息 |
| rebalance 频繁 | 消费者不稳定或会话配置不当 |
| 死信增长 | 数据格式或业务校验失败 |
| Broker 磁盘告警 | Broker 容量或保留策略问题 |

## 止损措施

低风险：

- 对非核心生产者限流；
- 暂停非必要批量生产；
- 隔离明确的毒消息并保留证据；
- 扩容消费者，但不得超过有效分区并行度。

需要审批：

- 修改分区数；
- 调整重试和死信策略；
- 跳过消费位点；
- 清空队列；
- 修改消息保留时间。

禁止为了快速消除告警直接重置 offset 或删除消息，这可能造成数据丢失或重复处理。

## 恢复验证

- lag 和最老消息年龄持续下降；
- 消费速率稳定高于生产速率，直至回到基线；
- 错误、重试和死信不再增长；
- 下游延迟恢复；
- 抽样验证消息最终状态；
- 记录是否存在重复消费及补偿需求。
